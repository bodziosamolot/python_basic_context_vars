01

The bug it fixes

Three requests run on one thread. Each stores its id, then awaits some I/O. While it waits, the event loop runs the others. A module global has one slot, so the last writer wins. A ContextVar gives each task its own slot.

Why each task? asyncio.gather() wraps every coroutine in a Task. Each Task runs inside its own copy of the context. That copy is the slot.

≈ [ThreadStatic] is wrong here: all three share one thread. Think AsyncLocal<T>.

02

Copy down, never up

Whether a child's write reaches the parent depends on one thing: did you start a new Task? A new Task gets a snapshot of the parent's context. A plain await runs the child in the parent's own context.

Same child, two ways to call it

Rule of thumb. create_task, gather, TaskGroup.create_task → copy. Bare await coro() → shared.

⚠ This is the opposite of C#, where an awaited async method's AsyncLocal writes do not flow back. See note 06.

03

Set, then reset

set() returns a Token that remembers the value from before the set. reset(token) puts it back. Treat it like a using block, so a value never outlives the work it was set for.

token = request_id.set("req-42")
try:
    await handle()            # all code below sees "req-42"
finally:
    request_id.reset(token)   # back to what was there before
  1. start"none"the default
  2. set("req-42")"req-42"token remembers "none"
  3. reset(token)"none"restored, not cleared

Restore, not default. reset() goes back to the value before that set, even if more sets came after it.

Python 3.14+: with request_id.set("x"): does the try/finally for you.

≈ Serilog's using (LogContext.PushProperty(…))

04

Crossing into threads

Each OS thread has its own current context. Whether your value follows you depends on whether the API copies the context across for you.

You callChild sees the value?Why
await f()sharedsame Task, same context
asyncio.create_task(f())copyTask snapshots the context
asyncio.to_thread(f)copycopies, then runs f inside it
loop.run_in_executor(None, f)nothe pool thread's own context
threading.Thread(target=f)noa new thread starts empty

Fix the two no rows by carrying the context yourself:

ctx = contextvars.copy_context()
await loop.run_in_executor(None, ctx.run, f)

Default to to_thread. It exists so you don't have to remember this table.

≈ copy_context() + ctx.run is ExecutionContext.Capture() + ExecutionContext.Run.

05

Three traps

  1. The copy is shallow

    A Task copies the reference. Mutate a list or dict and every task holding that reference sees it.

    log.set([])
await asyncio.create_task(child())   # child: log.get().append("x")
log.get()                            # ["x"]  — leaked up

    Store immutable values (str, tuple, frozen dataclass) and set() a new one to change it.

  2. Create it once, at module level

    Every ContextVar("x") call makes a new, unrelated variable. One built inside a function is a different key from the one you set elsewhere.

    def get_id():
    return ContextVar("request_id").get()   # always fails: brand new var

  3. No default means LookupError

    .get() on a var with no default and no value raises. Pass a default to the constructor, or to .get().

    user = ContextVar("user")
user.get()          # LookupError
user.get(None)      # None

Same with defaults. ContextVar("x", default=[]) hands the same list to every task that never set one.

06

Coming from C#

The model maps almost one to one onto AsyncLocal<T> and ExecutionContext. The rows marked differs are where your C# instincts will mislead you.

ContextVar[T]AsyncLocal<T>

Why the first difference? A C# async method restores the caller's ExecutionContext when it returns. A Python coroutine is just a function call on the same Task, so nothing is restored.
