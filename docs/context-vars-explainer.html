ContextVar · Context Python docs, "contextvars: Context Variables"

A key, a mapping, and a pointer

Three objects do the work. A ContextVar is only a key. It holds no value itself. A Context is a read-only mapping from those keys to values. Each thread has one current Context, and each Task carries its own. Every time the event loop resumes a Task, it makes that Task's Context current first.

request_id: ContextVar[str] = ContextVar("request_id", default="none")
user_id: ContextVar[int] = ContextVar("user_id")  # no default

How get() decides

  1. The value in the current context, if this variable has one there.
  2. Otherwise the default passed to get(), as in user_id.get(None).
  3. Otherwise the default passed to the constructor.
  4. Otherwise it raises LookupError.
C# / .NET

ContextVar ≈ AsyncLocal<T> and Context ≈ ExecutionContext. Both are immutable maps: a write builds a new map and makes it current. That's why a snapshot is cheap. copy_context() hands you the current map in O(1).

Where C# instincts mislead

In C#, an awaited async method gets a copy-on-write ExecutionContext, and its AsyncLocal writes are gone when it returns. In Python a bare await is a plain call on the same Task, so the write sticks. If you want isolation, start a Task.

Token · reset

Set, then reset

set() returns a Token that remembers the value from before the call. reset(token) puts that value back. Pair them in try/finally, the way you'd pair a constructor with Dispose(), so a value never outlives the work it was set for.

Python 3.7+try / finally

token = request_id.set("req-42")
try:
    await handle()           # everything in here sees "req-42"
finally:
    request_id.reset(token)  # back to what was there before

Where C# instincts mislead

.NET flows the ExecutionContext into Task.Run, ThreadPool.QueueUserWorkItem and new Thread() by default, and you opt out with ExecutionContext.SuppressFlow(). Python is the reverse: plain threads start empty, and you opt in.

A request id in every log line

The everyday use: set an id once in middleware, then read it anywhere below, including inside a logging filter, without adding a parameter to every function. This code is not part of this project, but it was run as shown.

request_id: ContextVar[str] = ContextVar("request_id", default="-")

class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id.get()  # read it, no parameter needed
        return True

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    incoming = request.headers.get("x-request-id") or uuid4().hex[:8]
    token = request_id.set(incoming)
    try:
        response = await call_next(request)
        response.headers["x-request-id"] = incoming
        return response
    finally:
        request_id.reset(token)

How the tests pin it down

Each test builds the scenario coroutine, then runs it with asyncio.run(). That call creates a fresh event loop, and its main Task runs on a copy of the test thread's context. Whatever a test sets stays inside that copy, so one test can't leak a value into the next.

def test_child_task_change_does_not_reach_parent():
    # Arrange
    scenario = parent_starts_child_task()

    # Act
    _, parent_sees = asyncio.run(scenario)

    # Assert
    assert parent_sees == "parent"

gotchas

Six ways to get it wrong

A mutable value leaks up

A Task copies the context, not the objects in it. Mutate a list and the parent sees the change.

log.set([])
await asyncio.create_task(child())  # child appends "x"
log.get()                           # ['x']

Store immutable values (str, tuple, frozen dataclass) and set() a new one. Same with default=[]: every Task that never set a value shares that one list.

A new ContextVar per call

The name is only a label. Identity is the object, so a var built inside a function is a new, unrelated key every time.

def get_id():
    return ContextVar("request_id").get("missing")  # always "missing"

Create each one once, at module level.

No default means LookupError

get() on a var with no value and no default raises. Pass a default to the constructor or to get().

LookupError: <ContextVar name='user_id' at 0x...>

Pool threads remember

A set() inside run_in_executor without ctx.run writes into the pool thread's own context. The next job on that thread reads it.

pool.submit(request_id.set, "leaked").result()
pool.submit(request_id.get).result()  # 'leaked'

Expecting await to isolate

A bare await helper() shares your context, so helper's set() stays after it returns. Use create_task when the helper must not change your values.

Generators share the caller's context

A generator has no context of its own. A set() in its body changes the context of whoever calls next(). PEP 568 proposed otherwise and was deferred.
